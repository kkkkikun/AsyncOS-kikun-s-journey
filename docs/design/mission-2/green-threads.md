## 学习：200行实现绿色线程 (有栈协程模型)

在精读了无栈协程的状态机模型后，我进一步对比研究了《200行实现绿色线程》这一有栈模型。

### 概念

"绿色线程（Green Thread）是由用户态调度器管理的线程，操作系统内核对其无感知。与之相对的是操作系统原生线程（OS Thread），后者由内核调度。'绿色'一词暗含'环保、轻量'，因为用户态切换的开销远小于陷入内核的系统调用。"

### 汇编上下文切换的具体步骤

> 上下文切换的汇编实现（以 x86-64 为例）：
> 1. **保存旧上下文**：将当前任务的 callee-saved 寄存器（rbx, rbp, r12-r15, rsp）压入其私有栈，并记录当前的栈顶指针（rsp）到该任务的 `TaskContext` 结构体
> 2. **切换栈指针**：将 CPU 的 `rsp` 寄存器修改为新任务的栈指针（从新任务的 `TaskContext` 中加载）
> 3. **恢复新上下文**：从新任务的栈中弹出它之前保存的寄存器值
> 4. **跳转执行**：执行 `ret` 指令，CPU 会自动弹出新任务的返回地址并跳转，从而无缝接续新任务的执行流

### 一个具体的运行时流程图

现在你的笔记是“特性罗列”，可以加一个**时序图**式的流程描述，让他人能在脑中“跑”起来：

> **完整流程示例**：
> ```
> 任务A执行中 → 调用 yield_task() 
> → 将自身放入就绪队列
> → 调用 swap(A.Context, Scheduler.Context)
> → CPU 的 rsp 切换到调度器的栈
> → 调度器从就绪队列取出任务B
> → 调用 swap(Scheduler.Context, B.Context)
> → CPU 的 rsp 切换到任务B的栈
> → 任务B从它上次 yield 的位置继续执行
> ```



### 核心机制差异
与 Future 依靠编译器将其拆解为 `enum` 结构体并在单栈上运行不同，绿色线程在堆上为每个任务分配了独立的上下文栈空间。

在绿色线程模型中，当一个任务因 I/O 阻塞时，它通过汇编把 CPU 让给【其他同样在用户态的**就绪任务**】，而不是把整个系统线程卡死。只有当【所有任务都阻塞】时，主调度器才会调用 `epoll_wait` 让出物理 CPU。这种‘内部自行消化切换’的机制，消除了传统线程频繁陷入内核态带来的高昂成本，从而实现了轻量的用户态线程。

其状态机变迁（Ready <-> Running）的底层驱动力不是依靠 `poll` 函数的反复重入与 Return，而是依赖底层汇编指令（如 `asm!`）进行**寄存器上下文的主动交换（Context Switch）**。


> 原文实现中使用简单的 `VecDeque<Task>` 作为 FIFO 就绪队列，这实现了最简单的协作式调度（先让出的任务排在队尾）。工业级实现（如 Go 的 GMP 模型）会引入更复杂的调度策略（抢占、工作窃取等），但基本原理相通。


### 执行流冻结的本质对比
- **无栈 Future**：当遇到阻塞时，调用 `return Async::NotReady` 彻底退出当前调用栈，依靠结构体内的字段记录断点。
- **有栈绿色线程**：当调用 `yield` 时，当前函数并没有 return。执行流在调用深处通过汇编强行保存当前的 `RSP`（栈指针）和通用寄存器至该任务的专属内存块中，随后将 CPU 的 `RSP` 覆写为主线程或另一就绪线程的栈顶。

这种机制的优点是业务代码无需包裹 `async/await`，对常规阻塞代码具有侵入性低的优势；但其代价是每个线程都需要预分配独立栈，内存开销显著高于无栈协程的单个 `enum` 大小。

> 另一个实际工程难题是**栈溢出**。因为每个绿色线程的栈空间是预分配的固定大小（如 2MB），如果任务递归过深或有大型栈变量，会导致未定义行为。而无栈协程（Future）的栈帧在编译期确定大小，没有这个问题。这也是**为什么 Rust 选择了无栈协程**的原因之一：**内存安全**不能妥协。
>
> 还有**原因**是**零成本抽象**的追求。Rust 核心哲学之一是“你不用的，你不为之付费”。有栈协程要求每个任务都预先分配独立栈，即使该任务只做极其简单的计算、完全不需要 2MB 栈空间，这份内存开销也必须付出。而无栈协程的 Future 状态机由编译器自动生成，大小完全由实际使用的变量决定，没有任何额外浪费。
>
> **更关键的一个分歧**在于**运行时的负担**。有栈协程需要调度器在用户态管理任务切换，这意味着运行时必须能够感知所有可能的阻塞点——因此几乎所有的系统调用都需要被重新封装，就像 Go 语言所做的那样：socket recv 并非真正的系统调用，而是建立在 epoll 之上的模拟层，底层 socket 工作在非阻塞模式，模拟层对外提供看似阻塞的接口。这个封装层使得 Go 拥有一个相当庞大的运行时库。而 Rust 的定位是一门系统编程语言，它无法像 Go 那样要求所有代码都运行在一个全知全能的运行时之上——Rust 必须能够直接调用操作系统原生的系统调用，必须能够与 C 语言库无缝互操作，必须能够在没有运行时的裸机环境中运行。早期 Rust 曾尝试过绿色线程（有栈协程），但在 0.7 版本之后就被移除了，正是因为一旦引入这样的机制，运行时也必须如 Go 一样封装全部系统调用，而 Rust 同时保留了原生线程（Native Thread），两者的 API 统一几乎不可能解决。无栈协程则干净地避开了这个困境：Future 只是一个普通的 trait，状态机只是一个普通的结构体，它们不需要任何运行时支持就可以在任何环境中执行[^2]。

### 与 Rust 无栈协程的对比表格

| 维度       | 有栈协程（绿色线程）   | 无栈协程（Future/async） |
| ---------- | ---------------------- | ------------------------ |
| 栈内存     | 每个任务独立栈（~2MB） | 单个 enum（编译期确定）  |
| 上下文切换 | 汇编保存/恢复寄存器    | 函数返回 + 状态机字段    |
| 阻塞语义   | `yield`，函数不返回    | `Pending` 返回，函数退出 |
| 代码侵入性 | 低（无需 async/await） | 高（async 传染）         |
| 内存安全   | 需处理栈溢出           | 编译期保证               |
