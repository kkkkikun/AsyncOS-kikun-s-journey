### 二、 核心并发模型理论工作原理

要深入分析实验数据，必须首先建立在三种并发模型于 Linux 操作系统层面的底层物理行为认知之上。

1. **多进程模型 (Process-Based Concurrency)**
* **物理机制**：进程是操作系统分配资源的最小单位。在多进程并发下，每个任务被完全隔离在自己独立的虚拟地址空间内，拥有专属于自己的页表（Page Table）、文件描述符表以及内存全局变量。
* **调度特征**：进程之间的控制权切换涉及内核态的重型切换（CPU 寄存器快照、内核栈、TLB 快照刷新），因此切换开销最高；但因为互不干扰，具备最强的安全隔离性。


2. **多线程模型 (Thread-Based Concurrency)**
* **物理机制**：线程是操作系统独立调度的最小单位。多线程运行在同一个父进程的虚拟地址空间内，共享所属进程的堆区、只读代码段以及全局数据，但每个线程保留自己独立的物理执行栈（Execution Stack）。
* **调度特征**：线程由 Linux 内核调度器（OS Scheduler）通过时间片轮转进行强占式调度（Preemptive Scheduling）。切换时虽然不需要刷新 TLB，但依然需要承担陷入内核态、保存/恢复寄存器上下文的硬件级开销。


3. **协作式异步协程模型 (Coroutine-Based Concurrency)**
* **物理机制**：协程在本实验中体现为基于 Rust async/await 的异步任务。它们通常作为用户态轻量任务运行，由异步运行时将大量任务调度到少量内核线程上执行，因此在 I/O 密集型场景下具有较低的调度与内存开销。
* **调度特征**：协程采用协作式调度（Cooperative Multitasking）。当某个异步任务遭遇网络 I/O 阻塞时，它会自发通过 .await 语法跳转出让执行权，用户态调度器直接在当前线程内移动指针切换至下一个 Future 状态机，整个过程完全免去了陷入内核态的物理摩擦。

### 三、 代码层面具体实现简述

在 Rust 语言的工业级工程落地中，三种模型分别依托了不同的底层并发原语：

1. **进程爬虫（混合线程-进程架构）**：借助 `std::process::Command` 机制派生子进程，并采用**混合线程-进程架构**。父进程为每个子进程通过 `std::thread::spawn` 创建专用的异步监控线程，该线程负责阻塞等待 `child.wait()` 并异步读取子进程的 stdout 标准输出管道流。这种非阻塞设计确保主循环始终保持响应性，避免进程回收成为串行瓶颈，同时通过参数控制让子进程作为专职爬取 Worker 运行。

2. **线程爬虫（Rayon 工作窃取线程池）**：采用基于 `rayon` 库的高级工作窃取线程池（Work-Stealing Thread Pool）架构。父进程通过 `rayon::ThreadPoolBuilder::new()` 构建固定规模的原生线程池，并利用并行迭代器 `par_iter()` 配合 `for_each()` 将任务分发到各个工作线程。每个工作线程维护独立的双端队列（deque），空闲线程可从其他线程队列尾部"窃取"任务，实现缓存友好的负载均衡。这种设计避免了手动通道同步的额外复杂性，并通过工作窃取机制实现了较低开销的任务分发与负载均衡。

3. **协程爬虫（无锁通道聚合架构）**：基于多线程异步运行时 **Tokio**。高并发的 HTTP 请求通过 `tokio::spawn` 被打包成轻量级的异步 Future 任务丢入主事件循环，并发水位由高性能的异步信号量 `tokio::sync::Semaphore` 进行低开销限流控制。在性能指标采集层面，我们摒弃了传统的异步 `Mutex` 方案，转而采用 `tokio::sync::mpsc::unbounded_channel` 无锁通道：3000+ 并发状态机将遥测数据发送至单一后台聚合任务，这种无锁聚合设计显著降低了高并发下的锁竞争，使协程模型在极限并发场景下仍能保持较高吞吐率和稳定性。

### 四、 性能特征捕获与数据采集方案

为了确保微基准测试（Micro-benchmark）数据背景的纯净与公平，本实验设计了高度严谨的底层无污染数据采集方案：

* **时间与吞吐量采集**：通过 std::time::Instant 记录宏观总耗时。吞吐率（Throughput）计算公式为 
  $$
  \text{RPS} = \frac{\text{总请求数}}{\text{总耗时}}
  $$

* 平均延迟与 P95 长尾延迟由高精度计时器对单任务的生命周期进行无盲区覆盖。

* **空间增量开销采集**：

**线程与协程版（峰值跟踪算法）**：

实现采用持续峰值跟踪而非简单的前后快照对比，具体流程如下：

1. **基线捕获**：在所有并发任务启动前（但初始化完成后），读取父进程的 `VmRSS` 作为基线 `baseline.current_rss_kb`
2. **峰值跟踪**：使用 `MemoryTracker` 持续监控进程内存状态，在任务执行过程中通过 `update()` 方法跟踪内存变化
3. **增量计算**：`peak_delta_mb()` 返回 `(peak_stats.peak_rss_kb - baseline_stats.current_rss_kb) / 1024`

**关键实现细节**（`src/utils/memory.rs:99-107, 125-130`）：
```rust
pub fn update(&mut self) -> Result<f64> {
    let current = MemoryStats::read_from_proc()?;
    if current.current_rss_kb > self.peak_stats.current_rss_kb {
        self.peak_stats = current;  // 持续更新峰值（包含 VmHWM）
    }
    Ok(self.delta_mb())
}

// 统一使用 VmHWM 进行峰值测量
pub fn peak_delta_mb(&self) -> f64 {
    (self.peak_stats.peak_rss_kb - self.baseline_stats.current_rss_kb) as f64 / 1024.0
}
```

> **重要改进**：统一使用 `peak_delta_mb()` 方法（基于 VmHWM）而非 `delta_mb()`（基于当前 VmRSS），确保测量的是**进程历史峰值内存**而非简单的当前值快照。这使得线程/协程版与多进程版的测量方法在语义上更加一致，都使用了 High Water Mark（最高水位线）的概念。

* **多进程版（Push 临终自报 + 扫描线算法）**：

为了跨越亚毫秒级执行下的轮询盲区，采用 **Push 临终自报架构**结合 **扫描线算法**：

**步骤 1：子进程自报**（`src/crawlers/process_crawler.rs:390-392`）
```rust
let memory_stats = MemoryStats::read_from_proc()?;
println!("__PEAK_RESIDENT_MEMORY_KB:{}", memory_stats.peak_rss_kb);
```
子进程在退出前夕读取 `/proc/self/status` 中的 `VmHWM` 字段（进程生命周期内的物理常驻内存最高水位线），通过 stdout 管道推送给父进程。

**步骤 2：父进程收集时间戳与内存数据**
父进程为每个子进程创建 `ProcessMemoryEvent`，记录：

- `start_time`：子进程启动时刻（微秒级精度）
- `end_time`：子进程结束时刻
- `peak_rss_kb`：子进程自报的 VmHWM 值

**步骤 3：扫描线算法计算全局并发峰值**
父进程将所有进程生命周期事件转换为时间轴上的 Start/End 事件，按时间戳排序后扫描：

```rust
for event in timeline_events {
    match event.event_type {
        EventType::Start => {
            current_concurrent_memory_kb += event.peak_rss_kb;
            if current_concurrent_memory_kb > peak_concurrent_memory_kb {
                peak_concurrent_memory_kb = current_concurrent_memory_kb;
            }
        }
        EventType::End => {
            current_concurrent_memory_kb -= event.peak_rss_kb;
        }
    }
}
```

这确保了在时间轴的任意时刻，都能准确计算出**当前并发存活的所有子进程的物理内存总和**，并从中提取全局峰值。

#### 两种内存采集方法的对比（统一使用 VmHWM）

| 维度 | 线程/协程版（峰值跟踪） | 多进程版（Push 自报） |
|------|------------------------|----------------------|
| **适用场景** | 单进程内多线程/多协程并发 | 多进程独立地址空间 |
| **数据来源** | 父进程自身的 `/proc/self/status` | 子进程自报的 stdout 管道 |
| **内存字段** | `VmHWM`（历史最高水位线） | `VmHWM`（历史最高水位线） |
| **计算方法** | `peak_delta_mb()` = VmHWM - baseline | 扫描线算法聚合并发峰值 |
| **精度保证** | 捕获执行期间真实峰值 | 捕获时间轴上任意并发重叠点 |
| **时间复杂度** | O(1) 更新，O(1) 查询 | O(N log N) 排序，O(N) 扫描 |
| **优势** | 实时跟踪，开销极低 | 跨进程边界，时间精度高 |
| **实现文件** | `src/utils/memory.rs:125-130` | `src/crawlers/process_crawler.rs:128-178` |

> **为什么多进程版需要更复杂的算法？**
>
> 1. **无法读取子进程内存**：父进程无法直接访问子进程的 `/proc/[pid]/status`（子进程可能已退出）
> 2. **避免轮询盲区**：高频轮询会错过亚毫秒级的内存峰值，Push 架构确保不遗漏
> 3. **并发峰值计算**：多个子进程生命周期重叠时，需要计算时间轴上的最大并发内存
>
> **算法健壮性优化**：扫描线算法在时间事件排序时采用**稳定排序策略**——当多个进程的 Start/End 事件具有完全相同的时间戳时（在高频执行场景下可能发生），算法强制 Start 事件优先于 End 事件处理。这确保了在时间戳冲突的边缘情况下，峰值内存计算依然准确，避免了因排序顺序不确定性导致的内存峰值低估风险。

#### 5.2 吞吐率对比分析

吞吐率是衡量爬虫系统单位时间内完成请求能力的核心指标。本实验中，吞吐率计算公式为：

$$
\text{RPS} = \frac{\text{成功完成的请求数}}{\text{总运行时间}}
$$

​	在 Pure_IO 负载下，协程模型的吞吐率整体最高。以 16 并发为例，进程、线程、协程三种模型的平均吞吐率分别为 315.16 RPS、8704.03 RPS 和 13720.31 RPS。协程模型约为线程模型的 1.58 倍，约为进程模型的 43.53 倍。该结果说明，在网络 I/O 等待占主导的场景下，协程能够用更少的内核线程承载更多的逻辑任务，避免为每个请求都创建独立的内核调度实体。

​	随着并发数继续增大，线程模型的吞吐率出现明显退化。线程模型在 16 并发时达到 8704.03 RPS，但在 512 并发下降到 3820.55 RPS，在 1024 并发下降到 1884.74 RPS，在 2048 并发时仅剩 538.50 RPS。这说明线程模型虽然比多进程轻量，但在线程数量过多时，内核调度器需要管理大量可运行实体，线程栈、上下文切换、调度队列维护和网络资源竞争会逐渐吞噬有效计算时间。

​	多进程模型的吞吐率曲线相对平坦，但平坦并不代表高效。它从 16 并发开始基本维持在 300 RPS 左右，在 3000 并发时下降到 276.15 RPS。该现象表明，多进程模型的主要瓶颈不是简单的并发不足，而是单个进程 Worker 的固定开销过高。每个子进程都需要独立地址空间、独立运行时初始化和独立资源回收，因此即使增加并发，也难以突破进程模型自身的固定资源成本。

​	协程模型在高并发下仍能保持较高吞吐率。虽然协程模型的吞吐率也会随着并发数过高而下降，例如从 16 并发的 13720.31 RPS 下降到 3000 并发的 4327.74 RPS，但其下降是平滑的，并未出现线程模型那样的断崖式成功率崩溃。这说明协程的瓶颈更多来自网络连接、Socket 缓冲区、事件循环调度压力以及任务队列长度，而不是大量内核线程带来的系统级调度风暴。

#### 5.3 延迟分布对比分析

​	延迟指标反映的是单个任务从开始执行到完成写入之间的生命周期长度。相比平均延迟，P95 延迟更能体现系统在高并发压力下的长尾表现。实验数据显示，三种模型在低并发下的延迟差距已经非常明显，在高并发下差距进一步扩大。

​	在 16 并发时，进程模型平均延迟为 50.00 ms，P95 延迟为 59.67 ms；线程模型平均延迟为 1.00 ms，P95 延迟为 2.33 ms；协程模型平均延迟为 1.00 ms，P95 延迟为 1.67 ms。此时线程和协程都可以将大部分请求压缩在极低延迟范围内，而进程模型由于进程级调度和启动回收成本，单任务延迟明显更高。

​	当并发数提升到 512 时，进程模型平均延迟达到 899.67 ms，P95 延迟达到 1663.33 ms；线程模型平均延迟为 107.00 ms，P95 延迟为 236.00 ms；协程模型平均延迟为 59.33 ms，P95 延迟为 114.00 ms。可以看到，协程不仅平均延迟低，长尾延迟也更稳定。线程模型虽然仍明显优于多进程模型，但随着内核线程数量增大，其 P95 延迟开始快速上升，说明调度延迟与资源竞争已经开始放大尾部请求的等待时间。

​	在 3000 并发极限场景下，线程模型平均延迟达到 5000.00 ms，P95 延迟达到 6493.00 ms，并且成功率只有 40.49%。这说明线程模型在该压力下已经不只是性能下降，而是进入资源饥饿与失败重试叠加的异常状态。相比之下，协程模型在 3000 并发下平均延迟为 497.00 ms，P95 延迟为 759.00 ms，成功率仍为 100.00%。协程模型的延迟虽然也随并发增加而上升，但系统仍处于可控状态，没有出现明显的崩溃边界。

#### 5.4 内存开销对比分析

​	内存开销是三种模型差异最直观的指标之一。从实验数据看，多进程模型的峰值内存随并发数增长最为剧烈，线程模型次之，协程模型整体最低且增长更平缓。

​	多进程模型在 8 并发时峰值内存为 100.12 MB，16 并发时为 197.75 MB，32 并发时为 394.66 MB，64 并发时为 794.41 MB，128 并发时为 1588.17 MB。这一组数据表现出近似线性增长规律，说明每增加一批子进程，系统都需要承担额外的独立地址空间、运行时、堆栈、文件描述符表以及相关元数据开销。按 8 到 128 并发区间估算，单个进程 Worker 的内存成本大约稳定在 12 MB 左右。到了 3000 并发时，多进程模型峰值内存达到 12831.17 MB，已经远高于线程和协程模型。

​	线程模型的内存增长也较明显，但远低于多进程模型。线程模型在 16 并发时峰值内存为 35.53 MB，128 并发时为 147.69 MB，512 并发时为 246.34 MB，1024 并发时为 354.51 MB，2048 并发时为 485.96 MB。线程共享同一进程地址空间，因此不需要像进程一样重复加载完整运行时环境，但每个线程仍需要独立栈空间和内核调度数据结构。随着线程数增加，线程栈、调度元数据和连接资源会共同推动内存增长。

​	协程模型的内存开销最低。在 16 并发时，协程模型峰值内存为 28.80 MB；128 并发时为 56.31 MB；512 并发时为 166.50 MB；1024 并发时为 249.55 MB；2048 并发时为 286.91 MB；3000 并发时为 226.05 MB。虽然个别高并发点受运行时内存复用、缓冲区回收时机和系统调度影响存在波动，但总体上协程模型以较低内存成本承载了最高的并发量。其原因在于协程任务主要表现为用户态的 Future 状态机和少量堆上状态，而不是一一对应的内核线程或进程。

> 需要说明的是，线程/协程版与多进程版的内存统计在测量对象上仍存在方法学差异：前两者反映单进程工作负载增量，多进程版反映并发子进程总和。因此，本节更适合用于比较三种模型的增长趋势与资源效率，而不宜将绝对数值做完全等价的横向解释。

#### 5.5 成功率与系统稳定性分析

​	成功率可以反映模型在极限并发下是否仍具备可靠性。实验数据显示，多进程模型和协程模型在所有并发配置下均保持 100.00% 成功率，而线程模型在 3000 并发时成功率下降到 40.49%。

​	多进程模型虽然吞吐率低、内存开销大，但由于进程之间相互隔离，单个任务失败一般不会直接破坏其他任务的地址空间，因此它在稳定性上表现较强。进程模型的代价是资源消耗巨大，尤其在高并发下会快速消耗物理内存和进程管理资源。

​	线程模型在 3000 并发下的成功率下降说明其已经触碰到系统资源边界。大量线程同时存在时，系统需要维护大量线程栈、调度实体和网络连接资源，容易触发文件描述符不足、连接建立失败、调度延迟过大或请求超时等问题。因此线程模型适合中等规模并发，但不适合无节制地将每个任务都映射为一个原生线程。

​	协程模型在 3000 并发下仍保持 100.00% 成功率，说明异步运行时能够更有效地控制任务调度和资源使用。协程模型并不是消除了网络和系统资源限制，而是通过少量内核线程承载大量用户态任务，显著降低了调度实体数量，使系统在极限并发下仍能保持较好的稳定性。

#### 5.6 Pure_IO 与 CPU_Bound_HTML 负载对比

​	除并发扩展实验外，本实验还在 16 并发下设计了 Pure_IO 与 CPU_Bound_HTML 两类负载对比，用于观察不同模型在 I/O 密集型与计算处理增强型任务中的性能变化。

| 负载类型 | 模型 | 总耗时/s | 吞吐率/RPS | 平均延迟/ms | P95延迟/ms | 峰值内存/MB | 成功率/% |
|---|---|---:|---:|---:|---:|---:|---:|
| Pure_IO | Process | 10.73 | 307.66 | 51.33 | 62.00 | 197.37 | 100.00 |
| Pure_IO | Thread | 0.39 | 8395.11 | 1.00 | 2.67 | 35.52 | 100.00 |
| Pure_IO | Coroutine | 0.25 | 13116.22 | 1.00 | 2.00 | 28.76 | 100.00 |
| CPU_Bound_HTML | Process | 11.04 | 298.96 | 52.67 | 64.67 | 198.57 | 100.00 |
| CPU_Bound_HTML | Thread | 1.35 | 2477.68 | 6.00 | 11.67 | 72.36 | 100.00 |
| CPU_Bound_HTML | Coroutine | 1.24 | 2655.47 | 5.67 | 11.33 | 77.53 | 100.00 |

​	从数据看，CPU_Bound_HTML 负载对线程和协程模型的影响更明显。线程模型吞吐率从 Pure_IO 下的 8395.11 RPS 降至 CPU_Bound_HTML 下的 2477.68 RPS，协程模型从 13116.22 RPS 降至 2655.47 RPS。其原因在于 Pure_IO 负载中任务大部分时间处于等待状态，协程可以通过 `.await` 让出执行权；而 CPU_Bound_HTML 负载增加了 HTML 解析、文本提取和处理计算，任务不再只是等待 I/O，而是需要实际占用 CPU 周期，因此异步调度带来的优势被部分削弱。

​	值得注意的是，在 CPU_Bound_HTML 负载下，线程模型与协程模型的吞吐率差距明显缩小。协程模型仍略高于线程模型，但二者不再像 Pure_IO 场景下那样相差数倍。这说明协程模型的核心优势主要体现在 I/O 密集型场景中；当任务逐渐转向 CPU 密集型时，系统瓶颈会从 I/O 等待转移到 CPU 计算能力，此时继续增加协程数量并不能线性提升性能。

​	多进程模型在两类负载下变化相对较小，Pure_IO 下吞吐率为 307.66 RPS，CPU_Bound_HTML 下为 298.96 RPS。这并不说明进程模型更适合 CPU_Bound_HTML，而是因为进程模型本身已经受到进程创建、运行时初始化和回收开销限制，负载类型变化带来的边际影响被其固定成本掩盖。

#### 5.7 合理性科学论证：从操作系统机制解释实验结果

​	第一，多进程模型的高内存与低吞吐是进程隔离机制的直接结果。进程是操作系统资源分配的基本单位，每个子进程都有独立虚拟地址空间、页表、栈、堆以及运行时环境。在本实验的 Worker 进程模型中，每个子进程都需要完成独立初始化，并在任务完成后由父进程回收。虽然这种模式具有最强的故障隔离性，但对于网页爬取这种短生命周期 I/O 任务来说，进程创建和销毁的固定成本远大于单次爬取本身的业务成本。因此，多进程模型即使提高并发数，吞吐率也长期停留在约 300 RPS 左右，无法像线程和协程一样显著扩展。

​	第二，线程模型在中低并发下具备较强性能，但在高并发下会受到内核调度压力限制。线程比进程轻量，共享父进程地址空间，因此在线程数适中时能够获得较高吞吐率。例如 16 并发时线程模型达到 8704.03 RPS，远高于进程模型。但线程仍然是内核调度实体，当线程数量增加到 1024、2048 甚至 3000 时，内核需要维护大量可运行线程、线程栈和调度状态，CPU 时间会被上下文切换、调度队列维护和资源竞争消耗。最终表现为吞吐率下降、P95 延迟上升，以及在 3000 并发下成功率下降到 40.49%。

​	第三，协程模型在 I/O 密集型任务中表现最优，是因为它将大量逻辑任务压缩到少量内核线程上执行。Rust 异步模型中的协程任务本质上是 Future 状态机，任务遇到 I/O 等待时通过 `.await` 主动让出执行权，由 Tokio 运行时在用户态调度其他就绪任务。与线程模型相比，协程切换不需要为每个任务都进行完整的内核线程上下文切换，因此在大量请求处于等待状态时，可以显著提高 CPU 利用效率和内存利用效率。本实验中协程模型在 3000 并发下仍保持 4327.74 RPS 和 100.00% 成功率，充分说明其适合高并发 I/O 场景。

​	第四，协程模型并非在所有负载下都绝对占优。CPU_Bound_HTML 实验显示，当任务中 CPU 处理比例增加时，协程相对于线程的优势明显缩小。Pure_IO 下协程吞吐率为 13116.22 RPS，线程为 8395.11 RPS；而 CPU_Bound_HTML 下协程为 2655.47 RPS，线程为 2477.68 RPS，二者差距明显缩小。这说明协程主要优化的是 I/O 等待期间的调度效率，而不是突破 CPU 计算能力上限。对于 CPU 密集型任务，合理的线程池规模、任务切分策略和多核并行能力反而更加关键。

​	第五，从单位内存效率看，协程模型也明显优于其他两种模型。以 3000 并发为例，多进程模型峰值内存为 12831.17 MB，吞吐率为 276.15 RPS；线程模型峰值内存为 419.28 MB，吞吐率为 121.96 RPS，且成功率只有 40.49%；协程模型峰值内存为 226.05 MB，吞吐率为 4327.74 RPS，成功率为 100.00%。这说明在同样的极限并发条件下，协程模型以最低的内存成本承载了最高的有效吞吐，是本实验场景下资源效率最高的实现方式。

#### 5.8 阶段性结论

​	综合吞吐率、延迟分布、内存开销与成功率四类指标，可以得到以下阶段性结论：多进程模型隔离性最好，但固定开销最大，适合对可靠隔离要求高、任务数量有限的场景；线程模型实现相对简单，在中低并发下性能较好，但随着线程数量增加，会受到内核调度和系统资源上限限制；协程模型在高并发 I/O 密集型任务中表现最佳，能够在较低内存占用下维持高吞吐和高成功率，但其优势会在 CPU 密集型任务中减弱。

### 六、 总结

​	本次实验围绕“基于进程、线程和协程的爬虫程序性能对比”展开，分别实现了多进程爬虫、基于 Rayon 线程池的多线程爬虫，以及基于 Tokio 异步运行时的协程爬虫。通过统一输入数据、统一输出格式、统一性能采集方式和多轮重复测试，实验从延时分布、吞吐率、内存开销和成功率四个维度比较了三种并发模型在爬虫任务中的表现。

​	从实验结果看，多进程模型的主要特点是隔离性强但资源开销大。由于每个子进程都拥有独立地址空间和独立运行时环境，多进程模型在内存占用上表现出近似线性增长趋势。随着并发数从 8 增长到 3000，其峰值内存从 100.12 MB 增长到 12831.17 MB，而吞吐率始终维持在约 276 到 315 RPS 的范围内，说明增加进程数量并没有带来有效吞吐的同比提升。对于短生命周期、高频率的网页爬取任务而言，进程创建、初始化和回收成本过高，因此多进程模型并不是最高效的实现方式。

​	线程模型在中低并发下表现良好。线程共享进程地址空间，相比多进程减少了大量资源重复加载，因此在 16 并发时达到 8704.03 RPS，显著优于多进程模型。然而，线程仍是内核调度实体，高并发下大量线程会带来线程栈开销、调度队列维护、上下文切换和网络资源竞争等问题。实验中线程模型在 1024 并发后吞吐率明显下降，在 2048 并发时仅为 538.50 RPS，在 3000 并发时成功率下降到 40.49%。这说明线程模型适合中等规模并发，但不适合将海量 I/O 任务直接映射为海量内核线程。

​	协程模型是本次实验中综合表现最好的模型。它在 Pure_IO 负载下充分发挥了异步 I/O 的优势，通过 Future 状态机和 Tokio 用户态调度器，将大量网络等待任务映射到少量内核线程上执行。在 16 并发时，协程模型达到 13720.31 RPS；在 3000 并发极限压力下，仍能保持 4327.74 RPS 和 100.00% 成功率，峰值内存仅为 226.05 MB。与线程模型相比，协程模型避免了为每个任务创建独立内核线程的高昂成本；与进程模型相比，协程模型避免了地址空间隔离带来的重复内存开销。因此，对于本实验中的高并发网页爬取任务，协程模型在吞吐率、稳定性和单位内存效率上都具有明显优势。

​	不过，实验也说明协程并不是对所有场景都天然最优。在 CPU_Bound_HTML 负载下，协程模型的吞吐率从 Pure_IO 场景的 13116.22 RPS 降低到 2655.47 RPS，线程模型也从 8395.11 RPS 降低到 2477.68 RPS，二者差距明显缩小。这说明当任务从 I/O 密集型逐渐转向 CPU 密集型时，系统瓶颈会从 I/O 等待转移到 CPU 计算本身。协程能够优化等待期间的调度效率，但不能突破 CPU 计算资源的物理上限。因此，在 CPU 密集型任务中，合理的线程池规模、任务划分方式和多核并行策略同样重要。

​	通过本次实验，我对进程、线程和协程的工作原理有了更直观的理解。进程强调资源隔离，代价是内存和创建回收成本较高；线程强调共享地址空间下的并行执行，适合中等并发，但高并发下会受到内核调度压力限制；协程强调用户态轻量调度，特别适合网络 I/O 这类大量等待、少量计算的任务。三者不是简单的优劣关系，而是适用于不同的任务场景。

​	最终，本实验得出的核心结论是：在高并发 I/O 密集型爬虫任务中，**协程模型具有最高的综合性能**；在线程数量可控的中低并发场景下，线程模型实现简单且性能可接受；在需要强隔离和故障边界的场景下，多进程模型仍有价值，但不适合作为大量短任务爬取的首选方案。对于实际工程中的爬虫系统，应优先采用异步协程模型作为核心并发架构，并结合限流、超时控制、错误重试和资源监控机制，以获得更高的吞吐率、更低的内存开销和更稳定的运行表现。

### 附录B：工程实践中的关键优化与问题解决

在实现三种并发爬虫的过程中，我遇到了多个工程挑战，并通过系统性的优化方案解决了这些问题：

#### 1. 无锁架构：消除高并发下的锁竞争瓶颈

**问题描述**：在协程爬虫的初始实现中，使用 `Arc<tokio::sync::Mutex<PerformanceMonitor>>` 来收集所有异步任务的性能数据。在 3000+ 并发场景下，所有任务竞争同一个互斥锁导致严重的任务排队，抵消了协程的非阻塞优势。

**优化方案**：重构为 `tokio::sync::mpsc::unbounded_channel` 无锁通道架构。
- 每个异步任务通过 `sender.send()` 将结果发送至无界通道
- 主任务通过 `receiver.recv()` 流式聚合结果，完全避免了用户空间锁竞争
- 消除了内核态的睡眠/唤醒上下文切换开销

**性能提升**：在极限并发下（3000+ 任务），吞吐量稳定性显著提升，消除了因锁竞争导致的延迟毛刺。

#### 2. 扫描线算法的稳定排序优化

**问题描述**：在多进程爬虫的内存峰值计算中，当多个子进程的 Start/End 事件具有完全相同的时间戳时，标准排序算法的顺序是不确定的。这可能导致在计算重叠内存时出现偏差。

**优化方案**：实现稳定排序逻辑，确保在时间戳相等时，Start 事件始终优先于 End 事件。
```rust
timeline_events.sort_by(|a, b| {
    match a.timestamp.cmp(&b.timestamp) {
        std::cmp::Ordering::Equal => {
            match (a.event_type, b.event_type) {
                (EventType::Start, EventType::End) => std::cmp::Ordering::Less,
                (EventType::End, EventType::Start) => std::cmp::Ordering::Greater,
                _ => std::cmp::Ordering::Equal,
            }
        }
        other => other,
    }
});
```

**效果**：确保了在边缘情况下峰值内存计算的准确性和可重复性。

#### 3. 混合监控架构：避免进程回收成为串行瓶颈

**问题描述**：如果父进程直接阻塞等待每个子进程（`child.wait()`），在高并发下会导致进程回收成为串行瓶颈，影响整体吞吐量。

**优化方案**：实现混合线程-进程架构。
- 父进程为每个子进程通过 `std::thread::spawn` 创建专用监控线程
- 监控线程负责阻塞等待 `child.wait()` 并读取 stdout 管道数据
- 父进程主循环保持非阻塞，持续调度新的子进程

**效果**：主循环始终保持响应性，进程回收与任务分发并行进行，最大化资源利用率。

#### 4. 内存跟踪精度：使用 VmHWM 替代 VmRSS 峰值

**问题描述**：直接读取 VmRSS（当前常驻内存）可能错过瞬时峰值，导致内存使用量被低估。

**优化方案**：在子进程自报架构中，使用 VmHWM（High Water Mark）字段，该字段记录了进程自启动以来的最大物理内存使用量，确保捕获真实的内存峰值。

**效果**：内存峰值测量的准确性和完整性得到保证。

### 附录C：VmHWM 测量原理与可靠性验证

#### 核心问题：VmHWM 是单进程维度的，如何可靠测量并发模型的内存占用？

**关键洞察**：VmHWM 确实是单进程维度的，但恰恰因为这个特性，它在两种并发模型中的可靠性不同：

| 并发模型 | VmHWM 可靠性 | 原因 |
|----------|-------------|------|
| **线程/协程版** | **完全可靠** | 所有并发单元在同一进程内，父进程的 VmHWM 包含全部 |
| **多进程版** | **完全可靠** | 每个进程独立，扫描线算法准确聚合 |

#### 详细分析

**线程/协程版（单进程包含所有并发单元）**：

```
父进程地址空间 (VmHWM: 35.24 MB)
├── 线程 1 栈 (8MB)
├── 线程 2 栈 (8MB)  
├── ...
├── 协程状态机 A (堆分配，几KB)
├── 协程状态机 B (堆分配，几KB)
├── ...
└── 共享堆 (HTTP 客户端、解析器等)
```

**为什么可靠？**
- 所有线程/协程共享同一个进程的虚拟地址空间
- 线程栈、协程状态机、堆分配都在同一个进程的物理内存中
- **父进程的 VmHWM = 所有并发单元的总内存占用**

**多进程版（扫描线聚合独立进程的 VmHWM）**：

```
时刻 T: 时间轴上并发存活的子进程
进程 A: ────────────── VmHWM: 13.35 MB
进程 B:   ──────────── VmHWM: 13.35 MB  
进程 C:     ────────── VmHWM: 13.35 MB
扫描线计算: 13.35 + 13.35 + 13.35 = 40.05 MB
```

**为什么可靠？**
- 每个子进程有独立的地址空间和独立的 VmHWM
- 进程间无共享内存，各自独立
- **扫描线聚合的总和 = 真实的系统级内存占用**

#### 验证方法

可以通过以下实验验证 VmHWM 的可靠性：

```bash
# 线程版：观察父进程 VmHWM 包含所有线程栈
cat /proc/[父进程PID]/status | grep VmHWM

# 多进程版：观察子进程 VmHWM 的独立性
cat /proc/[子进程PID]/status | grep VmHWM
# 每个子进程的 VmHWM ≈ 13.35 MB（独立且准确）
```

#### 结论

**VmHWM 的单进程特性正是它在并发模型中可靠性的基础**：

- 线程/协程版：利用了 VmHWM 的**包含性**（一个进程包含所有并发单元）
- 多进程版：利用了 VmHWM 的**独立性**（每个进程独立且可聚合）

**当前的测量方法对于各自并发模型内部的峰值捕获是可靠的，但在跨模型比较时仍需结合测量对象差异谨慎解读。**

### 附录D：工程优化实施记录

**重要声明**：线程/协程版与多进程版的内存测量存在**方法论上的根本差异**，直接数值对比并不完全公平，但反映的内存消耗特征是准确的。

**测量对象的本质差异**：

1. **线程/协程版**：测量**单进程的内存增量**
   ```
   父进程内存 = 基线内存 + 线程/协程工作负载增量
   测量值 = peak(VmHWM) - baseline(VmRSS)  ✅ 已统一使用 VmHWM
   ```
   - 捕获的是父进程地址空间内的**净增长**（使用历史最高 VmHWM）
   - 包括：线程栈、堆分配、共享数据结构
   - **优势**：反映了真实的工作负载内存代价
   - **局限**：无法区分共享开销与独占开销
   - **改进**：现在使用 `peak_delta_mb()` 基于 VmHWM，与多进程版峰值语义一致

2. **多进程版**：测量**多进程的并发内存总和**
   
   ```
   并发内存 = Σ(所有存活子进程的 VmHWM)
   测量值 = 扫描线算法的时间轴峰值
   ```
   - 捕获的是系统级的**物理内存占用**
   - 包括：每个进程的完整地址空间（栈、堆、代码段、数据段）
   - **优势**：反映了系统的真实资源消耗
   - **局限**：包含了进程隔离的冗余开销（如重复的代码段）

**改进：已统一峰值捕获机制**

| 对比维度 | 改进前 | 改进后 |
|----------|--------|--------|
| **内存字段** | VmRSS vs VmHWM | **VmHWM vs VmHWM ** |
| **峰值语义** | 当前值 vs 历史峰值 | **历史峰值 vs 历史峰值 ** |
| **测量一致性** | 较低 | **显著提高** |
| **数据可信度** | 需要谨慎解读 | **更直接可比** |

**剩余差异**（仍无法消除）：

虽然已统一使用 `VmHWM`，但两种方法的测量对象仍存在根本差异：

| 技术限制 | 线程/协程版为何不能用扫描线 | 多进程版为何不能用增量法 |
|----------|---------------------------|------------------------|
| **地址空间** | 线程共享进程空间，无法独立测量 | 进程独立空间，父进程无法访问 |
| **生命周期** | 线程/协程生命周期短暂，难以跟踪 | 子进程可能已退出，无法读取 `/proc/[pid]/status` |
| **时间精度** | 可以实时测量父进程内存 | 需要子进程自报避免轮询盲区 |
| **开销特性** | 共享内存，增量测量更准确 | 隔离内存，总和测量更准确 |

**数据解读建议**：

虽然两种方法的测量对象不同，但实验数据依然有效，只是**解读角度需要调整**：

| 场景 | 应关注的指标 | 解读方式 |
|------|-------------|----------|
| **资源配额规划** | 多进程版的绝对内存值 | 这是你需要为系统分配的物理内存 |
| **算法效率对比** | 三种模型的内存/吞吐量比值 | 协程的单位内存效率最高 |
| **成本估算** | 线程/协程版的增量值 | 这是你的工作负载真实内存代价 |
| **容量规划** | 多进程版的线性扩展系数 | 预测并发增加时的内存增长 |

**实验数据的可信度**：

​	尽管测量方法存在差异，实验数据依然稳定呈现出以下相对规律：协程模型的单位内存效率高于线程模型，多进程模型的内存增长近似线性，高并发下协程模型的内存增长斜率整体小于线程模型。
