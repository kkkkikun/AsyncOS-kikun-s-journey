### 问题一：存在三个网站无法爬取

#### 问题与解决

​	在向勇老师给出的 33 个高校网站中，我使用 AI 辅助编写的 Rust 简单爬虫在进行初步爬取时，发现有三个大学的网站主页无法正常获取。具体失败情况如下表所示：

| 学校 | 网站链接 | 失败类型 |
|------|----------|----------|
| 南京航空航天大学 | http://www.nuaa.edu.cn/ | 412 Precondition Failed |
| 湖南大学 | http://www.hunu.edu.cn/ | 503 Service Unavailable |
| 上海财经大学 | http://www.shufe.edu.cn/ | 超时 |

​	经过排查发现，想要成功爬取 “南京航空航天大学” 和 “上海财经大学”，必须将原表格中以 "http" 开头的链接改为 "https"。修改协议后这两所学校即可正常爬取，但 “湖南大学” 仍然报错无法访问。

​	在手动尝试访问该链接失败后，通过搜索引擎核对发现，原表格中给出的湖南大学链接有误（将 hnu 错写成了 hunu）。将其修正为真正的官网链接 "https://www.hnu.edu.cn/" 后，便可成功爬取。

#### 总结

​	在正式开始编写三种用户态爬虫之前，先写一个轻量级的简单爬虫来测试链路和数据的正确性是非常有必要的。这样可以提前清洗数据源，排除由于链接错误或安全策略导致的异常，避免后续开发核心功能时引入干扰。

### 问题二：网络访问不稳定

#### 问题与解决

​	修复链接之后，确实大部分时候都能爬下来所有学校的网站首页了，但是有时还是会由于网络波动等原因导致拉取失败。更重要的是，公网环境下的网络延迟（通常在数十毫秒至数百毫秒之间）具有极大的随机性与不可控性，而 Rust 各并发模型之间的调度开销差异往往在微秒级。如果直接使用公网请求进行压测，真实的性能差异将会被完全淹没在网络抖动的噪声中。

``` bash
   ────────────────────────────────────────────────────────────
🔍 [25/33] 正在爬取: 【中南大学】
   URL: https://www.csu.edu.cn/
   ✅ 状态码: 200 OK | 响应大小: 138412 bytes
   💾 成功保存: ./data/中南大学.txt
   ────────────────────────────────────────────────────────────
🔍 [26/33] 正在爬取: 【湖南大学】
   URL: https://www.hnu.edu.cn/
   ❌ 请求失败: error sending request for url (https://www.hnu.edu.cn/): operation timed out
   ────────────────────────────────────────────────────────────
🔍 [27/33] 正在爬取: 【中山大学】
   URL: https://www.sysu.edu.cn/
   ✅ 状态码: 200 OK | 响应大小: 108023 bytes
   💾 成功保存: ./data/中山大学.txt
   ────────────────────────────────────────────────────────────
```

​	所以，为了保证后续对比性能条件统一，并准确观测到不同并发模型在 CPU 调度、线程切换及 I/O 阻塞上的本质差异，我决定**采用“本地离线回环测试”的方案**。具体步骤如下：

1. **静态数据预缓存**：在测试前进行一次完整的、不计时的稳健抓取，将 33 所高校的首页 HTML 的文本完整下载到本地目录（如 `./data/`）。
2. **构建本地 Mock 服务器**：利用 Rust 的 `Axum` 框架，在本地 `127.0.0.1` 端口上搭建一个轻量级静态文件服务器，将缓存的高校首页数据发布出去。
3. **重定向基准测试**：将待测的三种 Rust 并发模型的请求目标全部重定向至本地服务器（例如将 `[https://www.hnu.edu.cn/](https://www.hnu.edu.cn/)` 映射为 `[http://127.0.0.1:8080/hnu_edu_cn](http://127.0.0.1:8080/hnu_edu_cn)`）。

**效果评估：** 这种做法带来了两个核心优势：

- **彻底消除外部噪声**：本地回环网络（Loopback）的延迟几乎为零且极其确定，排除了公网丢包、带宽限制和外部服务器限流的干扰。
- **保留真实的 I/O 行为**：相比于直接在代码中读取本地文件，通过本地 HTTP 服务器测试依然会触发操作系统的 TCP 三次握手、Socket 读写、系统调用（Syscalls）以及协议栈解析。这使得多线程同步阻塞、线程池异步非阻塞等模型在处理网络 I/O 时的调度效率能够被公平、准确地量化出来。

### 问题三：高并发下内存度量体系的异常

#### 问题与解决

​	在多进程爬虫套件进入 `--release` 优化与本地回环压测后，空间维度的度量数据连续遭遇了三次严重的系统级反常（幽灵进程显示 `0.00MB`、累计求和爆出 `478GB`、单体进程反常膨胀至 `145MB`）。经深层排查，这三种现象在底层并非孤立的 Bug，而是**多核高并发拓扑下，时间采样频率、空间聚合模型以及内核指标语义**发生系统级畸变的联动结果：

1. **时间维度（采样盲区）**：在极限加速下，子进程生命周期压缩至亚毫秒级（$\le 1\text{ms}$）。父进程主循环中 10ms 一轮的定时主动轮询（Pull）完全错过了子进程的生存期，导致监控流因“时间分辨率不足”产生大面积采样盲区。
2. **空间维度（时空错位）**：为补齐盲区改用子进程死后上报并用 `sum()` 盲目算术累加。由于总请求数被放大数百倍，该做法统计的实际上是空间资源在历史轴上的**全生命周期时间积分总量**（体积总和），而无法反映系统在某一瞬间承受的**瞬时最大并发物理挤压压力**。
3. **指标语义（虚实混淆）**：引入扫描线算法重构时空重叠后，数据仍显示 16 并发对应 2.3GB。根因在于代码误抓取了内核的 `VmPeak`（虚拟内存历史峰值）。当前 16 逻辑线程环境下，每个子进程一出生就会在内部拉起 16 个原生线程来组建 Tokio 线程池。内核为每个原生线程默认预留 8MB 虚拟栈，导致虚拟账本瞬间划走 $16 \times 8\text{MB}=128\text{MB}$，但根据 Linux **按需页分配（Demand Paging）机制**，这些未实际触碰的虚拟大饼根本没有映射任何物理页（RSS）。

​	**多维全栈重构对策：**

* **控制流升级（解时间盲区）**：彻底砍掉被动轮询，改用**子进程标准流临终自报（Push 架构）**。子进程在销毁前最后一纳秒，自行读取内核状态向 Stdout 管道安全刷新指标，由父进程异步非阻塞捕获。
* **拓扑流重构（解时空错位）**：父进程捕获每个子进程精确的 `spawn` 与 `reap` 微秒级时间戳，分别注册为 `Start`（内存步进 $+\Delta$）与 `End`（内存步退 $-\Delta$）事件。引入**时间扫描线算法（Sweep-line Algorithm）**流式扫过 chronological 排序的事件流，动态累加实时在线水位，精准提取**历史最高全局极大值（Global Maximum）**。
* **语义层校准（解虚实混淆）**：将子进程自报的内核抓取字段从虚拟峰值 `VmPeak` 彻底修正为 **`VmHWM`（High Water Mark，常驻物理内存最高水位线）**，彻底过滤 128MB 的虚拟栈水分。

​	**效果评估**：经过“时、空、语义”三位一体的无污染重构后，单子进程真实的物理常驻开销（RSS Peak）瞬间塌陷至极度准确的 **13.35 MB**，16 并发下的瞬时峰值内存精准回归至 **213.53 MB**，多进程模型随并发自变量阶跃的空间刚性特征被完美、公平地论证了出来。

#### 总结

​	微基准测试中的空间度量是一场多维协同的精密实验。我们必须认识到经典教科书理论与工业工程落地之间存在着隐性的“虚实断层”。评估高并发系统的资源弹性时，必须**从被动轮询走向临终自报**以对齐时间分辨率，**利用扫描线重构时空交点**以恢复时空对齐，并**严格纠正虚实指标语义**直击真实吃掉硬件页面的物理常驻开销（RSS），数据才具备硬核的系统工程选型价值。
