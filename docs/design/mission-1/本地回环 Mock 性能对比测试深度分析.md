### 二、 多维负载场景深度剖析



#### 1. 极限高并发质变点：线程模型的“雪崩”与协程的“弹性”

在**场景 4（3000 并发）**中，实验迎来了最核心的质变点。**线程爬虫的成功率发生灾难性暴跌，仅剩 0.45%**，几乎处于完全不可用状态；而**协程爬虫维持了 100.00% 的成功率**顺利通关，总耗时仅为 10.65 秒。

* **原因剖析：** 原生线程（OS Thread）是操作系统内核调度的重型资源。每创建一个内核线程，操作系统都需要为其分配独立的栈内存空间（Linux 默认通常为 2MB ~ 8MB）。当并发请求数瞬间拉高到 3000 时，系统因无法承受数 GB 内存的瞬间开销以及大量的线程描述符创建请求，导致了线程创建失败、内存耗尽或请求严重超时。

* **协程优势：** 与之形成鲜明对比的是，基于 Tokio 运行时的协程爬虫采用了 **M:N 用户态协作式调度模型**。3000 个并发任务在用户态仅仅表现为内存中的轻量级状态机（Task），底层依然复用与 CPU 核心数相匹配的少量内核线程。这种极低的资源摩擦使得协程在大规模高并发场景下展现出了绝对的弹性。



#### 2. 低并发长跑赛道：计算密集型任务拉平“线-协”差距

观察**场景 2（100 并发 / 16500 请求）**，在拉长测试周期后，线程爬虫（49.34s）与协程爬虫（48.80s）的总耗时和吞吐率表现出了高度的接近性，两者的差距缩小到了 1% 以内。

* **原因剖析：** 虽然异步网络 I/O 在协程中效率极高，但本项目的爬虫程序还包含了 **HTML 文本提取、移除无用标签（CPU 密集型任务）**。在并发数较低（100）且任务总量极大的长跑测试中，操作系统的线程切换开销不再是主要瓶颈，系统的整体瓶颈转移到了 CPU 解析 HTML 的算力上限上。这有力地证明了：**当系统处于低并发、纯 CPU 计算受限（CPU-Bound）的状态时，异步协程并不能带来超越多线程的提速效果**。



#### 3. 突发流量场景：内核切换开销拖慢“进程/线程”

在**场景 3（1000 并发 / 330 请求）**这种“并发数大于任务数”的瞬时冲击流场景下，协程（0.95s）再次领先了进程和线程（均为 2.90s）近 3 倍。

* **原因剖析：** 此时所有任务瞬间并发。进程和线程模型由于需要向内核申请高频创建大量的执行实体，其耗时大量被浪费在内核态与用户态的上下文切换（Context Switch）以及系统调用上。而协程在用户态的事件循环（Epoll驱动）可以无缝、高密度地分发网络请求，消除了这种硬性切换开销。



#### 4. 进程模型的“沉重代价”与稳定速率墙

通观四组实验，进程爬虫的吞吐率死死卡在 **105 ~ 113 任务/秒** 的区间内，展现出了极其死板的线性特征，在场景 2 中更是跑出了 156.14 秒的极长耗时。

* **原因剖析：** 进程是操作系统分配资源的最小单位。进程爬虫为每个 URL 都要经历完整的空间复制、地址空间分配（`fork`）、IPC 进程间通信以及进程销毁。数据表明，测试环境所用的 Linux 系统底层派生子进程的速率极限就在每秒 110 个左右。进程模型由于其过于沉重的生命周期，直接撞上了操作系统的“创建速度墙”。

### 三、 底层机理与选型总结



通过本次消除网络噪声的纯净基准测试，我们可以对三种 Rust 并发模型进行本质性的技术定性，从而指导生产环境的工程选型：



> **进程模型 (Process-based)**

> * **本质特征：** 强隔离、高摩擦。吞吐量受限于内核 `fork` 速率墙（约 110 RPS）。

> * **选型建议：** 绝不推荐用于高并发网络爬虫。但由于其具备天然的内存隔离和故障隔离特性，适合任务独立性极强、安全性要求极高、单次任务极重（如多媒体转码、不可信脚本执行）的非高并发场景。



> **线程模型 (Thread-based / 基于 Rayon 线程池)**

> * **本质特征：** 适合共享状态与共享内存计算，低并发下效率高，高并发下（并发 $\ge 1000$）易发生内核资源饥饿。

> * **选型建议：** 适合中等并发量（并发 $\le 500$）且伴随大量 CPU 密集型计算（如大数据清洗、本地数值计算、图像处理）的爬虫或后台系统。



> **协程模型 (Async/Await / 基于 Tokio 运行时)**

> * **本质特征：** 极轻量。通过用户态非阻塞事件驱动解决高并发 I/O 问题。在 3000+ 极限并发下展现出统领级的资源弹性。

> * **选型建议：** 海量网络爬虫、微服务网关、高并发 Web 服务的绝对首选。但在开发时需高度注意：**切勿在 async 块中直接执行未经过隔离的 CPU 密集型计算**（如沉重的 HTML 解析），否则会阻塞 Tokio 的工作线程，导致异步调度退化为同步等待。
