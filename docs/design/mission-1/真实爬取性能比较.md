## 真实网络测试数据局部分析

### 数据表现：并发模型的“性能归一”现象

在真实的公网环境下，请求 33 所高校官网首页的数据表现如下：

| 指标 | 进程爬虫 | 线程爬虫 | 协程爬虫 |
| :--- | ---: | ---: | ---: |
| 总耗时(秒) | 16.56 | 16.50 | 16.30 |
| 吞吐率(任务/秒) | 1.99 | 2.00 | 2.02 |
| 平均延迟(毫秒) | 2352 | 2378 | 2329 |
| P95延迟(毫秒) | 3628 | 4165 | 3069 |
| 成功率(%) | 100.00 | 100.00 | 100.00 |

​	从实测数据可以直观地看出，无论是总耗时（16.30s ~ 16.56s）、吞吐率（1.99 ~ 2.02 任务/秒），还是平均延迟（2329ms ~ 2378ms），进程、线程和协程三种并发模型表现出了**惊人的趋同性**。尽管协程在总耗时上略微领先 0.2 秒左右，但在统计学意义上，这种差距微乎其微。

### 原因剖析：网络 I/O 成了绝对瓶颈（Network-Bound）

为什么并发模型在这次测试中“失效”了？原因在于**系统瓶颈发生了转移**：

- **绝对时延的降维打击：** 操作系统的进程/线程上下文切换、或者 Rust Tokio 的用户态任务调度，开销都在微秒（$\mu s$）或纳秒（$ns$）级别。而本次公网请求的平均延迟高达 **2300+ 毫秒**（包含了跨网路由、DNS 解析、TCP 握手以及对方服务器的响应时间）。
- **瓶颈湮没效应：** 当单个任务中“等待网络响应”的时间，大于“并发模型自身调度开销”数百万倍时，并发模型的轻量与否就不再重要了。程序实质上被阻塞在网络 I/O 上，整个系统的吞吐量由公网带宽和目标服务器决定。

**唯独长尾延迟（P95）展现了微弱差异：** 协程的 P95 延迟（3069ms）比线程（4165ms）表现得更平滑。这说明在面对公网网络抖动、大量无序网络包涌入时，基于 `epoll` 异步非阻塞驱动的协程网络库（`reqwest`/`tokio`），在处理极端长尾延迟上比内核调度的多线程更具弹性。

### 优化方向：转向本地离线回环测试

为了真正测出“进程、线程、协程”三种模型在 Rust 工程实现中的**调度效率与资源摩擦差异**，必须消除公网这个最大的不可控变量。接下来的实验设计将做出两项关键调整：

#### 1. 采用本地离线回环测试（Local Loopback）

- **做法：** 提前将 33 所高校的 HTML 源码预取到本地缓存，或者在本地搭建一个极简的 Nginx / Mock 服务器，让爬虫通过本地回环网络（`127.0.0.1`）或纯文件 I/O 进行读取。
- **目的：** 将网络 RTT（往返时延）打消掉。当外部网络的巨型延迟被剥离后，系统瓶颈会瞬间重回操作系统的内核开销与运行时开销，从而逼出进程派生、线程切换、协程协作这三者在时间轴上的真实鸿沟。

#### 2. 引入“多轮压测与数据清洗”机制

在本地超低时延的环境下，微小的噪音（如操作系统的后台进程抢占、CPU 睿频波动、内存分配器缓存未命中）都会严重干扰毫秒级的测试结果。

- **做法：** 每一个负载测试都需要**连续跑 5 到 10 轮**。
- **数据处理：** 舍弃第一轮（包含冷启动和硬件缓存未命中的噪声数据），对其余多轮数据取平均值与标准差，确保最终得出的吞吐率和延迟具备统计学意义上的可复现性。
