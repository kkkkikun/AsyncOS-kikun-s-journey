# VmHWM 在并发模型内存测量中的可靠性分析

## 问题：VmHWM 是单进程维度的，如何测量并发模型的内存占用？

### 核心洞察

**VmHWM 确实是单进程维度的，但恰恰因为这个特性，它在两种并发模型中的可靠性完全不同。**

---

## 一、线程/协程版：VmHWM 是**完全可靠**的

### 原因：所有并发单元在同一个进程内

```
┌─────────────────────────────────────┐
│         父进程 (Rust 主程序)         │
│  ┌───────────────────────────────┐  │
│  │   VmHWM: 35.24 MB            │  │ ← 这一个 VmHWM 包含了所有内容！
│  └───────────────────────────────┘  │
│                                     │
│  ┌──────────┐ ┌──────────┐        │
│  │ 线程 1    │ │ 线程 2    │        │
│  │ 栈: 8MB   │ │ 栈: 8MB   │        │
│  └──────────┘ └──────────┘        │
│                                     │
│  ┌──────────┐ ┌──────────┐        │
│  │ 协程 A    │ │ 协程 B    │        │
│  │ 状态机    │ │ 状态机    │        │
│  │ (堆上)    │ │ (堆上)    │        │
│  └──────────┘ └──────────┘        │
│                                     │
│  ┌─────────────────────────────┐  │
│  │ 共享堆 (HTTP 客户端、缓存等) │  │
│  └─────────────────────────────┘  │
└─────────────────────────────────────┘
```

### 为什么可靠？

1. **地址空间共享**：所有线程/协程共享同一个进程的虚拟地址空间
2. **物理内存共享**：线程栈、协程状态机、堆分配、全局变量都在**同一个进程的物理内存**中
3. **VmHWM 准确记录**：Linux 内核会跟踪这个进程的常驻内存峰值，包含：
   - 所有线程的栈空间
   - 所有协程的状态机（堆分配）
   - 所有堆分配（HTTP 客户端、HTML 解析器等）
   - 全局数据结构

**结论**：对于线程/协程模型，**父进程的 VmHWM 就是所有并发单元的总内存占用**，测量是完全可靠的。

---

## 二、多进程版：需要扫描线算法，但依然可靠

### 原因：每个子进程独立，需要聚合

```
时刻 T: 时间轴上并发存活的子进程
────────────────────────────────────────────────────→
进程 A: ──────────────────────────────────
        VmHWM: 13.35 MB

进程 B:     ──────────────────────────────
            VmHWM: 13.35 MB

进程 C:       ────────────────────────────
                VmHWM: 13.35 MB

         ↑ 扫描线算法计算: 13.35 + 13.35 + 13.35 = 40.05 MB
```

### 为什么可靠？

1. **独立地址空间**：每个子进程有独立的 `/proc/[pid]/status` 和独立的 VmHWM
2. **无共享内存**：子进程之间没有共享堆、栈或全局变量
3. **内存隔离**：每个子进程的 VmHWM 就是它自己占用的物理内存
4. **聚合计算**：扫描线算法将所有并发子进程的 VmHWM 加起来，得到真实的系统级内存占用

**结论**：对于多进程模型，扫描线算法聚合的 VmHWM 总和就是真实的系统内存占用，测量是完全可靠的。

---

## 三、关键差异对比

| 维度 | 线程/协程版 | 多进程版 |
|------|------------|----------|
| **进程数量** | 1 个父进程 | N 个子进程 |
| **地址空间** | 1 个共享地址空间 | N 个独立地址空间 |
| **VmHWM 数量** | 1 个（父进程的） | N 个（每个子进程的） |
| **测量方法** | 直接读取父进程 VmHWM | 扫描线算法聚合 N 个 VmHWM |
| **可靠性** | ✅ 完全可靠 | ✅ 完全可靠 |
| **原理** | 所有并发单元在同一进程内 | 每个进程独立，需聚合 |

## 四、潜在问题与验证

### 问题 1：VmHWM 是否包含线程栈？

**答案**：✅ **包含**

```
/proc/self/status 中的 VmHWM 包含：
- 代码段
- 数据段 
- 堆段
- 所有线程的栈段
- 其他映射的物理内存
```

**验证方法**：
```bash
# 创建一个多线程程序，观察 VmHWM 变化
# 线程栈会占用物理内存，VmHWM 会相应增长
```

### 问题 2：协程的状态机在堆上，会被 VmHWM 捕获吗？

**答案**：✅ **会捕获**

```
协程状态机 = 堆分配的结构体
堆分配 → 物理内存 → VmRSS → VmHWM
```

**验证方法**：
```rust
// 协程状态机
enum CrawlStateMachine {
    Start(StartState),
    WaitingResponse(WaitingState),
    ParsingHTML(ParsingState),
    Done,
}

// 编译器将其转换为堆分配的 enum
// 堆分配会被计入 VmRSS，从而被 VmHWM 捕获
```

### 问题 3：子进程的 VmHWM 是否包含父进程的影响？

**答案**：❌ **不包含**

```
父进程 VmHWM = 只包含父进程自己的内存
子进程 VmHWM = 只包含子进程自己的内存

它们是完全独立的！
```

**验证方法**：
```bash
# 在进程爬虫运行时，分别观察父进程和子进程的 VmHWM
# 父进程 VmHWM ≈ 几十 MB（调度开销）
# 子进程 VmHWM ≈ 13.35 MB（worker 进程）
# 它们是独立的，不会互相影响
```

## 五、结论

### VmHWM 在两种并发模型中的可靠性

| 并发模型 | VmHWM 可靠性 | 原因 |
|----------|-------------|------|
| **线程/协程版** | ✅ **完全可靠** | 所有并发单元在同一进程内，VmHWM 包含全部 |
| **多进程版** | ✅ **完全可靠** | 每个进程独立，扫描线算法准确聚合 |

### 为什么这种方法是可靠的？

1. **线程/协程版**：利用了 VmHWM 的**进程级特性**——一个进程的所有资源都计入了 VmHWM
2. **多进程版**：利用了 VmHWM 的**进程隔离特性**——每个进程的 VmHWM 独立且准确，通过聚合得到总内存

### 潜在的改进空间

如果想进一步提高测量精度，可以考虑：

1. **线程/协程版**：可以额外测量每个线程的栈大小（`pthread_getattr_np`），但 VmHWM 已经包含了
2. **多进程版**：可以额外测量进程间通信的内存开销（管道缓冲区），但影响很小
3. **两者**：可以测量内核的内存开销（页表、文件描述符表），但这些通常被忽略

---

## 最终答案

**VmHWM 是单进程维度的，但恰恰因为这个特性：**

- ✅ 在**线程/协程版**中，单个进程的 VmHWM = 所有并发单元的总内存（完全可靠）
- ✅ 在**多进程版**中，扫描线算法聚合的 VmHWM 总和 = 系统总内存（完全可靠）

**因此，当前的测量方法在理论和实践上都是可靠的。**
